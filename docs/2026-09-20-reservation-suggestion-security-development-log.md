## 1. 왜 이 변경이 필요했나

기존 구조에서는 공간을 등록하고 예약 요청을 만들 수는 있었지만, 사용자가 **원하는 날짜에 실제로 이용 가능한 공간인지** 검색 단계에서 알기 어려웠다. 호스트도 매주 반복되는 운영 시간을 관리할 수 없었고, 승인된 예약으로 이미 차 있는 날짜를 별도로 조회할 수 없었다.

서비스 운영 측면에서도 사용자 건의를 수집·답변할 도메인이 없었고, 찜한 공간을 다시 찾는 흐름, 호스트 응답 품질을 확인하는 지표, 공간 등록 중간 저장이 부족했다. 한편 로그인 실패 응답이 계정 상태마다 달라 사용자 열거 공격이 가능했고, 관리자 URL 권한이 서비스 계층 검사에만 의존하는 문제도 있었다.

이번 변경은 단순 기능 추가가 아니라, 다음 흐름을 하나의 일관된 계약으로 만들기 위한 작업이다.

```text
공간 등록/임시저장
  → 반복 가용시간 설정
  → 날짜·지역·거리 기반 탐색
  → 예약 요청(수용 인원 검증)
  → 호스트 승인
  → 예약 완료 날짜 반영 및 알림
```

## 2. 설계와 구현

### 2.1 예약 가능일: 반복 규칙과 실제 예약을 분리

`SpaceAvailability`와 `SpaceBookedDate`를 분리했다.

- `SpaceAvailability`: `space_id`, `day_of_week`, `start_time`, `end_time`, `is_open`을 가진 **요일별 반복 가용시간 템플릿**이다. V10에서 생성한다.
- `SpaceBookedDate`: 승인된 매칭의 `space_id`, `date`, `matching_id`를 기록하는 **특정 날짜의 예약 완료 상태**다. V14에서 생성한다.

이 분리는 “매주 월요일은 열지만, 다음 주 월요일은 이미 예약됨”을 표현하기 위한 것이다. 하나의 `is_available` 플래그로 둘을 함께 표현하면 반복 운영 정책과 개별 예약 사실이 섞여 갱신·조회 규칙이 복잡해진다.

호스트는 `PUT /spaces/{space-id}/availability`로 슬롯 목록을 교체하고, 누구나 `GET /spaces/{space-id}/availability`, `GET /spaces/{space-id}/booked-dates`로 조회한다. 매칭 승인 시 `MatchingService`가 공간 내부 API를 호출해 예약 완료 날짜를 기록하며, 승인 전에는 기록하지 않는다.

`GET /spaces?date=YYYY-MM-DD`는 다음 두 조건을 함께 사용한다.

1. 해당 날짜의 요일에 `is_open=true`인 반복 가용 슬롯이 하나 이상 있어야 한다.
2. 같은 날짜의 `SpaceBookedDate`가 없어야 한다.

JPQL에서 nullable `date`를 단독으로 검사할 때 PostgreSQL이 파라미터 타입을 추론하지 못했던 오류는 `dateProvided` boolean을 분리해 해결했다. 날짜는 `bd.date = :date`처럼 타입이 확정되는 비교식에서만 사용한다.

**얻은 효과:** 사용자는 예약 불가능한 후보를 검색 단계에서 줄일 수 있고, 호스트의 장기 운영 규칙을 매 예약마다 다시 입력하지 않아도 된다. 도메인 데이터도 반복 정책과 실제 예약 이력으로 명확히 분리된다.

### 2.2 탐색 경험: 관심 목록, 집계, 지역·거리 정렬

- `GET /spaces/me/liked`: 로그인 사용자의 관심 공간을 공통 `PageResponse<T>` 형식으로 반환한다.
- `GET /spaces/counts/by-category`, `GET /spaces/counts/by-region`: 필터 UI·탐색 화면에 필요한 집계 값을 제공한다.
- `GET /spaces?lat={lat}&lng={lng}`: 두 좌표가 모두 들어오면 거리순으로 정렬한다. 일반 정렬은 `createdAt` 또는 `likeCount`를 사용한다.

실제 지오코딩 API를 아직 연결하지 않았기 때문에 V9의 8개 권역(`Region`)과 V15의 대표 좌표를 사용한다. 기존 주소는 `sido` 값으로 권역을 백필했고, `RegionCoordinates`와 V15의 좌표 테이블 값은 반드시 같이 유지해야 한다.

**얻은 효과:** 좋아요가 일회성 토글로 끝나지 않고 재방문 탐색으로 이어진다. 거리 정렬의 API 계약과 저장소 구조를 먼저 확보했기 때문에, 이후 카카오·네이버 등 지오코더로 정확한 주소 좌표를 채워도 호출 방식은 유지할 수 있다.

**정확도 한계:** 현재 거리순은 권역 중심점 근사치다. 같은 권역 내 두 공간의 실제 거리는 구분할 수 없으므로 “인근 정밀 검색”으로 홍보하면 안 된다. 실제 지오코딩 도입 시 좌표 정밀도, 실패 재시도, 주소 수정 시 재지오코딩 정책을 추가로 설계해야 한다.

### 2.3 건의함: 사용자 피드백을 독립 도메인으로

`modules/suggestion`을 새 Gradle 모듈로 만들고 V13에서 `suggestions.suggestions` 테이블을 생성했다. 상태는 `PENDING`, `ANSWERED`이며 작성자·제목·본문·답변 내용·답변 시각을 보관한다. 작성자별 최신순 인덱스와 전체 최신순 인덱스를 추가했다.

| API | 권한 | 목적 |
| --- | --- | --- |
| `POST /suggestions` | 로그인 사용자 | 건의 등록 |
| `GET /suggestions/me` | 로그인 사용자 | 내 건의 목록 조회 |
| `GET /admin/suggestions` | 관리자 | 전체 건의 목록 조회 |
| `PATCH /admin/suggestions/{suggestion-id}/answer` | 관리자 | 답변 등록 및 상태 전이 |

컨트롤러·서비스·엔티티·예외·보안 설정을 모듈 안에 함께 둬 관심사를 분리했고, 관리자 응답에서는 내부 사용자 ID 대신 사용자 이름을 조회해 운영 화면에 필요한 정보를 제공한다.

**얻은 효과:** 운영 이슈가 채널 밖에서 유실되지 않고, 처리 상태와 답변 이력을 남길 수 있다. 향후 카테고리, 첨부파일, SLA, 알림을 추가할 때도 suggestion aggregate 안에서 확장 가능하다.

### 2.4 공간·회원·매칭 정보 확장

- 공간: 면적, 수용 인원, 층, 주차 정보, 이용 단위(`HOURLY`/`DAILY`)를 V7 및 생성·수정 DTO에 추가했다. 상세·목록·관리자 응답에도 반영했다.
- 공간 상태: V11에서 `DRAFT`를 관리자 상태 제약에 추가해 작성 중인 공간을 공개·심사 흐름과 구분했다.
- 회원: 프로필 이미지 URL, 전화번호, 소개 문구를 프로필/수정 계약에 포함했다.
- 매칭: `guest_count`를 V8에 추가하고, 예약 생성 시 공간 수용 인원을 넘으면 차단한다.
- 호스트 통계: `GET /matchings/hosts/{host-id}/stats`는 전체 요청 대비 승인·거절 처리 비율과, 처리된 요청의 평균 응답 시간(생성~갱신 시각, 분)을 반환한다.

**얻은 효과:** 검색 조건과 실제 공간 상세 정보의 간극을 줄이고, 호스트가 신뢰도·응답 품질을 개선할 수 있는 측정 기반을 마련했다. `DRAFT`는 미완성 공간이 공개 검색에 노출되는 문제도 막는다.

### 2.5 알림 의존성 방향 정리와 페이지네이션 통일

기존에는 alarm 모듈이 matching에 의존했다. 이를 `AlarmInternalApi`로 역전해 matching이 alarm을 호출하도록 바꿨다. 예약 생성, 승인, 거절, 취소의 네 지점에서 상대방에게 알림을 만든다.

또한 `PageResponse<T>`를 common으로 올리고 공간·팝업·좋아요·건의함 등의 개별 페이지 응답 타입을 제거·통일했다.

**얻은 효과:** alarm이 특정 예약 도메인에 묶이지 않아 재사용성이 커졌고, 순환 의존 위험이 줄었다. 프론트는 목록 API마다 다른 pagination envelope를 해석하지 않아도 된다.

## 3. 보안과 안정성 개선

### 로그인 사용자 열거 방지

이전에는 없는 이메일, 탈퇴 계정, 비밀번호 불일치가 각각 다른 예외·상태 코드(예: 404/410/401)와 메시지로 노출될 수 있었다. 공격자는 로그인 API만 반복 호출해 가입 여부를 추정할 수 있었다.

`AuthService.authenticateWithUser()`에서 `UserNotFoundException`, `DeletedUserException`, `InvalidPasswordException`을 모두 잡아 동일하게 다음 응답으로 변환한다.

```text
401 Unauthorized
이메일 또는 비밀번호가 일치하지 않습니다.
```

이는 실패 원인을 사용자에게 덜 자세히 알려주는 대신 계정 존재 여부라는 민감한 정보를 보호하는 선택이다. 로그인 성공·실패의 응답 시간 차이가 크게 남지 않는지도 운영 환경에서 추가 관찰할 필요가 있다.

### 경계 보안과 입력 검증

- `/admin/spaces/**`, `/admin/suggestions/**`에 `hasRole("ADMIN")`를 명시했다. 서비스의 역할 검사와 별개로 HTTP 진입점에서 차단하는 방어 심층화다.
- 회원가입 비밀번호에 최소 8자, 전화번호에 `^01[0-9]{8,9}$` 형식 검증을 추가했다. 프로필 수정의 전화번호에도 동일 규칙을 적용했다.
- 사용자·매칭·관리자 영역의 디버그성 오류 문구를 실제 사용자에게 전달 가능한 문장으로 바꾸고, Bean Validation 오류에서 영문 필드명이 노출되지 않도록 예외 응답을 정리했다.
- 예약 인원이 공간 수용 인원을 넘는 요청을 `MatchingService.validateGuestCount`에서 거절한다.

## 4. 개발 환경과 OAuth 개선

`S3Config`는 `AWS_ACCESS_KEY_ID`와 `AWS_SECRET_ACCESS_KEY`가 모두 존재하면 정적 자격증명을 사용하고, 비어 있으면 AWS SDK의 `DefaultCredentialsProvider`로 폴백한다. 따라서 로컬 `.env` 기반 업로드와 ECS/App Runner 등의 IAM 역할 기반 운영을 함께 지원한다.

OAuth 콜백은 JSON을 직접 표시하는 대신 `frontend.base-url`을 기준으로 프론트 콜백 경로로 302 리다이렉트하고 access/refresh token을 전달한다. 브라우저 기반 로그인 완료 흐름을 만들기 위한 변경이다.

### 운영 전 반드시 확인할 항목

1. `docker-compose.yml`에서는 AWS 관련 환경 변수 전달을 제거했지만 `application.yaml`은 이를 읽는다. 로컬 업로드가 필요하면 `.env` 또는 Compose의 별도 secret 전달 경로가 실제로 준비돼 있어야 한다.
2. OAuth 토큰을 URL 쿼리로 전달하면 브라우저 기록, 프록시 로그, referrer에 남을 수 있다. 단기적으로 callback 페이지에서 즉시 URL을 정리하고, 장기적으로는 one-time code나 HttpOnly 쿠키 교환 방식으로 바꾸는 것이 안전하다.
3. `SpaceBookedDate`는 승인 시 기록된다. 다일 예약을 허용한다면 시작일만이 아니라 예약 구간의 모든 날짜를 기록·해제하는 정책인지 실제 요구사항과 테스트로 확인해야 한다.
4. 예약 승인 경쟁 조건은 공간별 매칭을 비관적 잠금으로 조회해 겹침을 확인한다. 동시 승인 부하와 취소 후 booked-date 정합성은 통합 테스트로 보강해야 한다.

## 5. 검증 기록과 다음 검증

### 보고된 검증

- `./gradlew compileJava` 통과
- 로그인 실패 응답 통일: curl 확인
- 회원가입 검증 메시지: API 호출 확인
- 공간 검색 날짜/거리 필터: API 호출 확인
- 수용 인원 초과 예약 차단: API 호출 확인

### 이 기록 기준으로 재현할 검증 시나리오

1. 존재하지 않는 이메일·탈퇴 계정·잘못된 비밀번호가 같은 401 상태와 같은 body를 반환하는지 확인한다.
2. 일반 사용자 토큰으로 `/admin/spaces/**`, `/admin/suggestions/**` 접근 시 403인지 확인한다.
3. 월요일 가용 공간에 월요일 예약을 승인한 뒤 `GET /spaces?date=해당월요일`에서 제외되는지 확인한다.
4. 같은 공간의 겹치는 예약 두 건을 동시에 승인 시도해 하나만 승인되는지 확인한다.
5. `PUT availability` 후 조회 결과의 요일·시간·공개 여부가 정확한지, 호스트가 아닌 사용자가 변경하면 거절되는지 확인한다.
6. 좌표가 있는 공간과 없는 공간, 서로 다른 권역의 공간으로 거리 정렬·페이지네이션을 확인한다.
7. 로컬 `.env` 정적 키와 키 없는 IAM 역할 환경에서 각각 S3 업로드를 확인한다.

| 질문 | 답변 핵심 |
| --- | --- |
| 반복 가용시간과 예약 완료 날짜를 왜 나눴나? | 반복 정책과 특정 날짜의 사실은 변경 주기와 의미가 다르다. 분리해야 휴무·운영시간 수정이 과거 예약 이력에 영향을 주지 않는다. |
| 날짜 검색은 어떻게 보장하나? | 요청 날짜에서 요일을 계산해 열린 `SpaceAvailability`가 존재하는지 확인하고, 동일 날짜 `SpaceBookedDate`는 없어야 한다. 두 조건을 모두 만족하는 공간만 반환한다. |
| 거리 정렬이 정확한가? | 현재는 권역 대표 좌표라 근사 정렬이다. API와 저장소 구조를 먼저 만들었고, 후속 지오코딩 도입으로 정밀도를 올릴 계획이다. 한계를 명확히 인지하고 있다. |
| 사용자 열거를 어떻게 막았나? | 존재하지 않음·탈퇴·비밀번호 불일치 예외를 인증 계층에서 하나로 묶어 동일한 401과 동일 메시지만 노출했다. |
| 서비스 레이어 권한 검사만으로 부족한 이유는? | 호출 경로가 늘거나 서비스가 재사용될 때 경계를 놓칠 수 있다. HTTP 보안 설정과 서비스 검사를 함께 둬 방어 심층화를 했다. |
| OAuth 토큰을 쿼리로 넘기는 방식의 위험은? | 브라우저/프록시 로그 노출 가능성이 있다. 현재는 프론트 완료 흐름을 우선 복구한 것이고, 다음 단계에서 일회성 code 교환 또는 HttpOnly 쿠키로 바꿔야 한다. |
